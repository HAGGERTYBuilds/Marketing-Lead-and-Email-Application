### 1e. Record Pat / Record Liam

### 1f. List-Unsubscribe header: not possible on this path
The Sender sends through Microsoft Graph (Outlook draft, then send).
Graph only accepts custom `internetMessageHeaders` whose names start with
`x-`, so `List-Unsubscribe` and `List-Unsubscribe-Post` are refused. The
Outlook node has no header option either. The visible one-click link in
the footer is what this path can do. A real header needs a sending
service that allows it (Mailchimp, SES, SendGrid).

### 1g. Sticky note
Change "A failed draft or send is recorded as failed..." to say a run that
dies before Outlook made the draft is put back in the queue, and one that
dies after is failed and never retried.

## 2. New workflow: Haggerty Mr. Workflow Verify

Checks people waiting on Evaboot before a campaign may send to them, using
the same Evaboot call as Haggerty Verify Queued Emails (gmTku02FReIruWNZ).
1 credit per person. Without this workflow they wait, and after the Sender
has nothing else left the campaign stays "sending" with them waiting, so
turn it on together with the SQL.

Settings: timezone America/Los_Angeles, errorWorkflow jwbd5a9mDJrfeuKc.

1. **Every 10 Min Workday**: Schedule, cron `*/10 7-16 * * 1-5`.
2. **Next To Verify**: Postgres, Execute Query, `HAGGERTY Supabase`:
   ```sql
   select * from public.bulk_verify_next(20);
   ```
   (Hands out up to 20, each at most once per 15 minutes, and counts the try.)
3. **Ask Evaboot**: HTTP Request, copy of the node in gmTku02FReIruWNZ:
   POST `https://api.evaboot.com/v1/email-validation/single/`,
   genericCredentialType / httpHeaderAuth `Evaboot`, JSON body
   `={{ JSON.stringify({ email: $json.email }) }}`, timeout 40000,
   response `neverError: true`, `onError: continueRegularOutput`.
4. **Read Verdict**: Code, run once for all items:
   ```js
   // safe | riskier | suspect | invalid, or '' when Evaboot gave no verdict
   // (no credits, still running, outage). '' three times leaves them out.
   const picked = $('Next To Verify').all();
   return $input.all().map((it, i) => {
     const r = it.json || {};
     const p = r.prospect || (r.data && r.data.prospect) || r;
     const v = String((p && p.email_validity) || '').toLowerCase();
     return { json: {
       recipient_id: String(picked[i].json.recipient_id).replace(/[^0-9a-fA-F-]/g, ''),
       validity: ['safe', 'riskier', 'suspect', 'invalid'].includes(v) ? v : ''
     } };
   });
   ```
5. **Record Verdict**: Postgres, Execute Query:
   ```sql
   select public.bulk_verify_record($1::uuid, $2) as result;
   ```
   Query parameters: `={{ [ $json.recipient_id, $json.validity ] }}`

Safe goes into the send queue; riskier, suspect and invalid are left out
with the reason on their row (the contact's email_status is updated too).

## 5. Haggerty Verify Queued Emails (gmTku02FReIruWNZ)

Keeps the behaviour (an Evaboot failure never empties Pat's board) but
records it, so the board shows "NOT VERIFIED" on that person and the send
is marked `sent_unverified`.

### 5a. Read Verdict (Code)
Replace the code with:

```js
// Evaboot answers safe, riskier, suspect or invalid. Anything else (no
// credits, still running, an outage) leaves the contact unverified and on
// the board, and is now recorded with the reason.
const picked = $('Needs Check').all();
const out = [];
$input.all().forEach((it, i) => {
  const r = it.json || {};
  const p = r.prospect || (r.data && r.data.prospect) || r;
  const v = String((p && p.email_validity) || '').toLowerCase();
  const src = picked[i] && picked[i].json;
  if (!src) return;
  const ok = ['safe', 'riskier', 'suspect', 'invalid'].includes(v);
  const why = ok ? '' : ('Evaboot did not answer: ' + (r.status === 'running' ? 'still checking'
    : (r.error && (r.error.message || r.error)) || r.message || r.detail || 'no verdict')).toString().slice(0, 280);
  out.push({ json: {
    contact_id: String(src.contact_id).replace(/[^0-9a-fA-F-]/g, ''),
    email: src.email, validity: ok ? v : '', reason: why
  } });
});
return out;
```

### 5b. Save Verdict (Postgres)
Replace the query (which built SQL from strings) with a parameterised call:

```sql
select public.verify_save($1::uuid, $2, $3) as result;
```

Query parameters: `={{ [ $json.contact_id, $json.validity, $json.reason ] }}`

`verify_save` does what the old query did for a verdict (save
email_status and email_verified_at, take an invalid address off today's
queue) and, for no verdict, stamps `email_queue.verify_missed_at` and
`verify_missed_reason` on today's row.

## 6. New workflow: Haggerty Photo Cleanup

Removes photos the PM marked Not approved from the public `photo-review`
bucket after the batch is sent back. Only batches sent back after the SQL
ran are touched (`remove_due_at` is set by `photo_review_finish`); nothing
already in the bucket is deleted.

Settings: timezone America/Los_Angeles, errorWorkflow jwbd5a9mDJrfeuKc.

1. **Every Hour**: Schedule, cron `15 * * * *`.
2. **Photos To Remove**: Postgres, Execute Query, executeOnce:
   ```sql
   select coalesce(jsonb_agg(item_id), '[]') as ids,
          coalesce(jsonb_agg(file_path), '[]') as paths,
          count(*) as n
     from public.photo_review_to_remove(100);
   ```
3. **Any?**: If `{{ $json.n }}` > 0.
4. **Delete From Bucket**: HTTP Request, DELETE
   `https://ekatzukprjpisdiwubjq.supabase.co/storage/v1/object/photo-review`,
   Authentication: predefined credential type `supabaseApi`,
   credential `HAGGERTY Marketing Supabase` (service key), JSON body
   `={{ JSON.stringify({ prefixes: $json.paths }) }}`.
   (Direct deletes from storage.objects in SQL are blocked by Supabase,
   so this must go through the Storage API.)
5. **Mark Removed**: Postgres, Execute Query:
   ```sql
   select public.photo_review_mark_removed(array(select jsonb_array_elements_text($1::jsonb)::uuid)) as removed;
   ```
   Query parameters: `={{ [ JSON.stringify($('Photos To Remove').first().json.ids) ] }}`

The laptop copy task needs no change: it only copies `decision = 'approved'`.
